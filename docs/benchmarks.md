# 성능 측정

> 아래 수치는 **개발용 Mac의 JVM에서 측정한 값**입니다. Android 기기에서 측정한 값이 아니므로 보장 수치로 사용하지 마세요.

## 방법

`./gradlew :pulse-okhttp:benchmark` (`CaptureOverheadBenchmark`)

- 같은 JVM 안에서 루프백 MockWebServer로 작은 JSON GET 요청을 보냅니다(실제 네트워크 지연 없음).
- PULSE 없음, 메타데이터만 수집, 메타데이터와 JSON 본문 수집의 세 가지 구성을 라운드마다 번갈아 실행합니다.
- 라운드당 요청 200개, 워밍업 10라운드, 측정 30라운드입니다. 라운드 평균(µs/요청)의 중앙값과 p95를 구합니다.
- 수집 큐와 마스킹까지 포함하고, 저장소(Room과 파일 쓰기)는 제외한 채 빈 sink를 사용합니다. 저장은 별도 스레드에서 처리되므로 요청 경로에 포함되지 않습니다.
- JSON 마스킹도 저장 스레드에서 처리하므로, 본문 수집 모드에서 요청 경로에 더해지는 비용은 바이트 복사뿐입니다.

## 결과 (2026-10-13, JVM 25.0.3, macOS aarch64)

같은 명령을 세 번 실행한 결과입니다. 단위는 요청당 µs입니다.

| 실행 | PULSE 없음(중앙값) | 메타데이터만(차이) | 메타데이터 + 본문(차이) |
| --- | --- | --- | --- |
| 1 | 39.4 | +12.1 | +11.2 |
| 2 | 58.4 | +11.5 | +7.1 |
| 3 | 112.6 | +21.9 | +34.0 |

- 이 환경에서 요청당 추가 시간은 중앙값 기준 약 7~34µs였습니다. 문서의 목표(메타데이터 모드에서 요청당 2ms 이하)보다 작지만, **실제 기기에서 다시 측정해야 합니다.**
- 실행마다 기준값의 편차가 컸습니다(39~113µs). 측정 중에 같은 컴퓨터에서 다른 작업이 돌고 있었고, p95는 수백 µs까지 튀었습니다. 차이 값만 참고하세요.

## 아직 하지 않은 것

- Android 기기와 에뮬레이터에서의 측정(Jetpack Benchmark/Macrobenchmark), 메모리 사용량, 1만 건 목록 스크롤 시 프레임.
- 저장소 쓰기 처리량(초당 트랜잭션)과 큐가 가득 찼을 때 버려지는 비율.
