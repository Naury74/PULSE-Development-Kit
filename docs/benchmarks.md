# 성능 측정

> 아래 숫자는 **개발용 Mac의 JVM에서 잰 값**입니다. Android 기기에서 잰 값이 아니며, 보장 수치로 쓰지 마세요.

## 방법

`./gradlew :pulse-okhttp:benchmark` (`CaptureOverheadBenchmark`)

- 같은 JVM 안의 루프백 MockWebServer에 작은 JSON GET을 보낸다(실제 네트워크 지연 없음).
- 세 구성을 라운드마다 번갈아 돈다: PULSE 없음 / 메타데이터만 / 메타데이터 + JSON 본문.
- 라운드당 요청 200개, 워밍업 10라운드, 측정 30라운드. 라운드 평균(µs/요청)의 중앙값과 p95를 낸다.
- 수집 큐와 마스킹까지 포함하고, 저장소(Room·파일 쓰기)는 빼고 빈 sink를 쓴다. 저장은 별도 스레드라 요청 경로에 들어가지 않는다.
- JSON 마스킹도 저장 스레드에서 하므로 본문 모드의 요청 경로 비용은 바이트 복사뿐이다.

## 결과 (2026-10-13, JVM 25.0.3 · macOS aarch64)

같은 명령을 세 번 돌린 결과. 단위는 요청당 µs.

| 실행 | PULSE 없음(중앙값) | 메타데이터만(차이) | 메타데이터 + 본문(차이) |
| --- | --- | --- | --- |
| 1 | 39.4 | +12.1 | +11.2 |
| 2 | 58.4 | +11.5 | +7.1 |
| 3 | 112.6 | +21.9 | +34.0 |

- 요청당 추가 시간은 이 환경에서 중앙값 기준 약 7~34µs였다. 문서의 목표(메타데이터 모드에서 요청당 2ms 이하)보다 작지만, **기기에서 다시 재야 한다.**
- 실행마다 기준값이 크게 달랐다(39~113µs). 측정 중 같은 컴퓨터에서 다른 작업이 돌았고, p95는 수백 µs까지 튀었다. 차이 값만 참고한다.

## 아직 하지 않은 것

- Android 기기·에뮬레이터에서의 측정(Jetpack Benchmark/Macrobenchmark), 메모리 사용량, 1만 건 목록 스크롤 프레임.
- 저장소 쓰기 처리량(초당 트랜잭션)과 큐가 넘칠 때의 버림 비율.
